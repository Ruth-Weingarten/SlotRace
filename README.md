# SlotRace – קביעת תורים לאסיפת הורים

> **SlotRace** הוא שם הקוד של הפרויקט, והוא מתאר את האתגר הטכני של השרת: תחרות על סלוטים. המשתמשות רואות את המערכת בשם **SchoolSlot**.

**SchoolSlot** היא מערכת שבה מחנכת מפרסמת זמנים פנויים (סלוטים) לאסיפת הורים, והורים מזמינים בעצמם תור עבור הילדה שלהם, בלי מזכירות ובלי אישור ידני.
הפרויקט הוא שרת **ASP.NET Core (.NET 10)** עם **PostgreSQL**, בנוי ב-**Clean Architecture**, עם הרשמה והתחברות ב-**JWT**, שני תפקידים (מחנכת והורה), ותיעוד מלא ב-**Swagger**.

---

## המשאב המוגבל: סלוט אחד, הזמנה אחת

**המשאב:** סלוט (זמן פגישה) אצל המחנכת. לכל סלוט יכולה להיות הזמנה אחת בלבד, ולכל ילדה תור אחד בלבד.

**איפה התחרות:**
1. **שתי הורות מזמינות את אותו סלוט באותו רגע.** שתיהן קוראות את הסלוט כשהוא פנוי, ושתיהן עוברות את הבדיקה "הסלוט פנוי?".
2. **אבא ואמא של אותה ילדה מזמינים באותו רגע סלוטים שונים.** שניהם עוברים את הבדיקה "לילדה אין תור?".

**איך המערכת מונעת הזמנה כפולה – שלוש שכבות:**

| מנגנון | מה הוא עוצר | איך |
|---|---|---|
| **טרנזקציה** (`IUnitOfWork`) | שמירה חלקית | כל הבדיקות והשמירה הן יחידה אחת: הכול או כלום |
| **Concurrency token** (`Slot.Version`) | שתי הורות על **אותו סלוט** | ה-`UPDATE` נשלח עם `WHERE Version = @old`. השמירה הראשונה מחליפה את ה-`Version`, ולכן אצל השנייה 0 שורות מתעדכנות, ו-EF זורק `DbUpdateConcurrencyException` |
| **אינדקס ייחודי חלקי** על `Slots.StudentId` | אבא ואמא על **שני סלוטים שונים** לאותה ילדה | מסד הנתונים עצמו דוחה את השמירה השנייה (הפרת ייחודיות, קוד 23505) |

**איך המערכת מגיבה:** ה-repository מתרגם את חריגות EF ל-`SlotConflictException`, והשירות מחזיר **409 Conflict** עם הודעה ברורה, למשל: *"הסלוט נתפס על ידי הורה אחרת. נסי סלוט אחר."*. שום דבר לא נשמר בהזמנה שנדחתה.

**ההוכחה:** הבדיקה `ConcurrencyTests` מריצה שני `DbContext` נפרדים על אותו מסד (SQLite בזיכרון) ומוכיחה ששתי השמירות לא מצליחות שתיהן.

## ארכיטקטורה

| פרויקט | תפקיד |
|---|---|
| `SlotRace.Domain` | ישויות (`User`, `Student`, `Slot`) ו-`Role`. בלי חבילות חיצוניות |
| `SlotRace.Application` | ממשקים, שירותים (לוגיקה עסקית), DTOs, AutoMapper, `ServiceResult`. לא מכירה EF, HTTP, BCrypt או JWT |
| `SlotRace.Infrastructure` | EF Core ו-PostgreSQL, repositories, טרנזקציה, BCrypt, יצירת JWT, migrations ונתוני דמו |
| `SlotRace.API` | Controllers, Middleware, אימות והרשאות, Swagger, NLog |
| `SlotRace.Tests` | בדיקות יחידה (xUnit + Moq) ובדיקת שני DbContext |

כיוון התלויות: `API → Application ← Infrastructure`, וכולן → `Domain`. הממשקים יושבים ב-Application, והמימושים ב-Infrastructure (היפוך תלויות).

## הרצה מקומית

**דרישות:** .NET 10 SDK, Docker.

**1. מסד נתונים (PostgreSQL ב-Docker):**
```bash
docker run --name pg-slotrace -e POSTGRES_PASSWORD=<סיסמה> -p 5432:5432 -d postgres:16
```

**2. סודות (User Secrets).** מתוך התיקייה `SlotRace.API`:
```bash
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Port=5432;Database=SlotRaceDb;Username=postgres;Password=<סיסמה>"
dotnet user-secrets set "Jwt:Key" "<מחרוזת אקראית באורך 32 תווים לפחות>"
dotnet user-secrets set "Registration:TeacherCode" "<קוד מורה לבחירתך>"
```
הסודות לא נמצאים ב-repository. השרת לא יעלה אם `Jwt:Key` חסר או קצר מ-32 תווים.

**3. הרצה:**
```bash
dotnet run --project SlotRace.API
```
בעלייה השרת מריץ לבד את כל ה-migrations, ואם המסד ריק, ממלא נתוני דמו. אין צורך בשום פקודה ידנית.

**4. Swagger:** `https://localhost:7256/swagger`
מתחברים ב-`POST /api/auth/login`, מעתיקים את ה-`token`, לוחצים **Authorize** ומדביקים.

## בדיקות

```bash
dotnet test
```
- **בדיקות יחידה (xUnit + Moq):** `AuthService`, `SlotService` (כולל כל החוקים של ההזמנה, ומקרה שבו ההזמנה נדחית בתחרות) ו-`StudentService`, כולל בדיקות פרטיות (שם הילדה וקוד ההצטרפות).
- **בדיקת שני DbContext (SQLite בזיכרון):** שתי הורות על אותו סלוט, ואבא ואמא על שני סלוטים לאותה ילדה. בשני המקרים השמירה השנייה נכשלת, ובמסד נשארת הזמנה אחת.
